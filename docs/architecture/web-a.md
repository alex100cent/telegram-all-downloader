## Реализованный путь

1. MAIN script в `document_start` наблюдает создание Worker и его протокол. Он не открывает вторую Telegram-сессию.
2. Сохраняет ограниченный индекс ID аккаунта, ID чата/сообщения, ID и свойств вложения. Оригинальные сообщения, подписи, телефоны, ключи и initApi args не сохраняются и не анализируются. `accessHash` чата используется как параметр маршрутизации сообщения только в памяти страницы.
3. DOM-кнопка привязана к `data-list-key` и конкретному `messageId`. Метаданные аудиоплеера, имя файла и соседние сетевые запросы не участвуют в выборе файла.
4. При наличии маршрута чата выполняется `fetchMessage` для конкретного ID. Ответ с другим чатом/сообщением отклоняется.
5. Документы, музыка, voice, video, round video, animation, stickers читаются через `downloadMedia` порциями до 512 KiB. В ответе проверяются полный размер и длина порции. Смещения используют безопасные целые JS без усечения до 32 бит.
6. Фото использует полный `photo<ID>` без thumbnail-параметров. Telegram сначала буферизует полное фото; адаптер допускает этот отдельный путь до 32 MiB и затем выдаёт небольшие порции writer. Для больших документов этот путь не применяется. Предел проверяется по полученному фото: это не обещание ограничения внутренней аллокации Telegram до ответа.
7. TGS сохраняется в исходном gzip-контейнере. JSON после декомпрессии отклоняется; GIF из MP4 не создаётся.
8. Остановка worker, смена аккаунта, удаление/замена вложения, несоответствие размера, таймаут и отмена завершаются явной ошибкой. Частичные обновления состояния применяются только к белому списку метаданных; сообщения с `ttlSeconds`, включая одноразовые voice/кружочки, исключены.
9. У каждого подготовленного источника есть версия метаданных. Исчезновение записи из ограниченного индекса или snapshot Telegram само по себе не доказывает удаление сообщения: клиент очищает и заново наполняет `messages.byChatId` при синхронизации. При таком изменении адаптер повторяет точный `fetchMessage` через сохранённый маршрут чата и принимает источник только при совпадении всей подписи вложения: аккаунта, чата, сообщения, media ID, типа, имени, MIME и размера. Штатный `fetchMessage` выполняет серверный `GetMessages`, а не чтение локального кэша. Отсутствие сообщения, edit, TTL и смена аккаунта по-прежнему завершаются ошибкой. Обновление, пришедшее во время RPC, не перезаписывается старым ответом: выполняется одна повторная проверка, затем ошибка при продолжающейся гонке. При неизменном индексе дополнительных RPC на каждый chunk нет.

Собственные RPC имеют уникальный префикс. Listener удаляет только свои ответы из смешанного batch; остальные события Telegram продолжают работать. Поздние ответы отменённых запросов поглощаются. Callback загрузки не связан с play/pause.

Вкладки без активного API Worker используют родной `BroadcastChannel tt-global_<accountSlot>` с тем же ограниченным списком операций. Глобальные обновления принимаются пассивно и сразу сокращаются до метаданных. Наблюдение устанавливается также на создаваемые самим Telegram каналы этого аккаунта: у каждого канала отдельный structured-clone Blob, поэтому для просмотра важен объект из события, полученного клиентом. Расширение не отправляет `requestGlobal`: неверный APP_VERSION в этой команде заставляет Telegram перезагрузиться.

Прямая Worker-отмена передаётся через `cancelProgress` с правильным ID. В родном межвкладочном протоколе Telegram внешний ID запроса отличается от внутреннего worker ID; гарантия отмены уже отправленной порции через этот путь отсутствует. Расширение сразу прекращает запись и планирование новых порций, но одна уже отправленная порция до 512 KiB может завершиться в клиенте. Одновременные `read` одного источника запрещены. Это не докачка и не обещание мгновенного обрыва сетевого запроса.

## Обнаружение и ограничения

- Основной список и обычные альбомы имеют точную DOM-привязку. При отсутствии метаданных учитывается стабильная `.media-inner` внутри того же `.Message[data-message-id]`, поскольку фото, видео и стикеры используют CSS modules. Preview ссылок и цитат исключаются, а файл определяется только ответом `fetchMessage` на точные ID, не URL картинки. Неоднозначный элемент и платный preview не превращаются в кнопку скачивания.
- В открытом просмотрщике кнопка появляется, когда ID источника доказан progressive URL либо связью полученного Blob и `createObjectURL`, и этот media ID однозначно связан с одним обнаруженным сообщением. Cache-hit фото покрывается пассивным наблюдением уже выполняемого Telegram `Cache.match` → `Response.blob` для media-ключей текущего origin: расширение не делает дополнительных cache reads. Повторное использование одного media ID в нескольких сообщениях остаётся неоднозначным; скачивание из сообщения работает без этой неоднозначности.
- Для каналов/supergroups ссылка истории ведёт в точное сообщение через штатный `tgaddr=tg://privatepost?channel=...&post=...`, сохраняя account slot. Для личных чатов и обычных групп сохраняется ссылка в исходный чат. Проверено по [routing.ts](https://github.com/Ajaxy/telegram-tt/blob/28ffcf710b15571e5a2f7bb3bdce3fc90fc8ec80/src/util/routing.ts), [Main.tsx](https://github.com/Ajaxy/telegram-tt/blob/28ffcf710b15571e5a2f7bb3bdce3fc90fc8ec80/src/components/main/Main.tsx) и [deepLinkParser.ts](https://github.com/Ajaxy/telegram-tt/blob/28ffcf710b15571e5a2f7bb3bdce3fc90fc8ec80/src/util/deepLinkParser.ts); живой переход требует проверки в браузере.
- Изменения контракта Telegram могут потребовать обновления адаптера. При отсутствии известной формы данных адаптер возвращает ошибку, а не превью или случайный трек.
- После установки/обновления расширения Telegram нужно перезагрузить, чтобы наблюдение началось до создания worker.
- Тесты с искусственным worker проверяют точное аудио при одинаковых названиях, альбомы, диапазоны больше 4 GiB, отмену и поздние ответы, mixed batches, смену аккаунта, TGS, неполные ответы, partial diffs/delete, разные BC Blob objects, cache-hit viewer, TTL и одновременные read. Они не являются доказательством реального скачивания файла такого размера.
