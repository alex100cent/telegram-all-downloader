## Implemented path

1. The MAIN script observes Worker creation and its protocol at `document_start`. It does not open a second Telegram session.
2. It keeps a bounded index of account IDs, chat/message IDs, and attachment IDs and properties. Original messages, captions, phone numbers, keys, and initApi args are neither stored nor analyzed. The chat `accessHash` is used as a message routing parameter only in page memory.
3. The DOM button is bound to `data-list-key` and a specific `messageId`. Audio player metadata, filenames, and nearby network requests do not participate in file selection.
4. When a chat route is available, `fetchMessage` is called for the specific ID. A response for a different chat/message is rejected.
5. Documents, music, voice messages, videos, round videos, animations, and stickers are read through `downloadMedia` in chunks of up to 512 KiB. The response is checked for total size and chunk length. Offsets use safe JS integers without truncation to 32 bits.
6. Photos use the full `photo<ID>` without thumbnail parameters. Telegram first buffers the entire photo; the adapter permits this separate path up to 32 MiB and then passes small chunks to the writer. This path is not used for large documents. The limit is checked against the received photo: it does not guarantee a limit on Telegram's internal allocation before the response.
7. TGS is saved in its original gzip container. Decompressed JSON is rejected; MP4 is not converted to GIF.
8. Worker termination, account changes, attachment deletion/replacement, size mismatches, timeouts, and cancellation end with an explicit error. Partial state updates are applied only to an allowlist of metadata fields; messages with `ttlSeconds`, including one-time voice messages/round videos, are excluded.
9. Each prepared source has a metadata version. A record disappearing from the bounded index or a Telegram snapshot does not by itself prove that the message was deleted: the client clears and repopulates `messages.byChatId` during synchronization. On such a change, the adapter repeats the exact `fetchMessage` through the saved chat route and accepts the source only if its entire attachment signature matches: account, chat, message, media ID, type, name, MIME, and size. The native `fetchMessage` performs a server `GetMessages` call rather than reading the local cache. A missing message, an edit, TTL, and account changes still result in an error. An update arriving during the RPC is not overwritten by the old response: one recheck is performed, followed by an error if the race continues. An unchanged index does not trigger extra RPCs for each chunk.

The extension's RPCs use a unique prefix. The listener removes only its own responses from mixed batches; other Telegram events continue to work. Late responses to canceled requests are consumed. The download callback is independent of play/pause.

Tabs without an active API Worker use the native `BroadcastChannel tt-global_<accountSlot>` with the same restricted set of operations. Global updates are received passively and immediately reduced to metadata. Observation also covers channels that Telegram itself creates for this account: each channel has its own structured-clone Blob, so the object from the event received by the client matters for the viewer. The extension does not send `requestGlobal`: an incorrect APP_VERSION in this command causes Telegram to reload.

Direct Worker cancellation is sent through `cancelProgress` with the correct ID. In Telegram's native protocol between tabs, the external request ID differs from the internal worker ID; cancellation of an already requested chunk through this path is not guaranteed. The extension immediately stops writing and scheduling new chunks, but one already requested chunk of up to 512 KiB may complete in the client. Concurrent `read` calls on the same source are prohibited. This does not provide download resumption or promise immediate termination of the network request.

## Discovery and limitations

- The main list and regular albums have exact DOM bindings. When metadata is missing, the stable `.media-inner` within the same `.Message[data-message-id]` is considered because photos, videos, and stickers use CSS modules. Link and quote previews are excluded, and the file is identified only by the `fetchMessage` response for exact IDs, not by the image URL. Ambiguous items and paid previews do not receive a download button.
- In the open viewer, a button appears when the source ID is established by a progressive URL or by the relationship between the received Blob and `createObjectURL`, and this media ID maps unambiguously to one discovered message. Cached photos are covered by passively observing Telegram's existing `Cache.match` → `Response.blob` calls for media keys on the current origin: the extension does not perform additional cache reads. Reusing one media ID in multiple messages remains ambiguous; downloading from the message avoids this ambiguity.
- For channels/supergroups, the history link opens the exact message through the native `tgaddr=tg://privatepost?channel=...&post=...`, preserving the account slot. For private chats and regular groups, a link to the original chat is saved. Verified against [routing.ts](https://github.com/Ajaxy/telegram-tt/blob/28ffcf710b15571e5a2f7bb3bdce3fc90fc8ec80/src/util/routing.ts), [Main.tsx](https://github.com/Ajaxy/telegram-tt/blob/28ffcf710b15571e5a2f7bb3bdce3fc90fc8ec80/src/components/main/Main.tsx), and [deepLinkParser.ts](https://github.com/Ajaxy/telegram-tt/blob/28ffcf710b15571e5a2f7bb3bdce3fc90fc8ec80/src/util/deepLinkParser.ts); live navigation still requires a browser check.
- Changes to Telegram's contract may require adapter updates. When the expected data shape is unavailable, the adapter returns an error rather than a preview or an unrelated track.
- Telegram must be reloaded after installing/updating the extension so that observation starts before worker creation.
- Tests with a simulated worker cover exact audio selection with identical names, albums, ranges beyond 4 GiB, cancellation and late responses, mixed batches, account changes, TGS, incomplete responses, partial diffs/deletion, different BC Blob objects, a viewer using cached media, TTL, and concurrent reads. They do not prove that a real file of that size has been downloaded.
