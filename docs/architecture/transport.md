# Передача файла и жизненный цикл

В первой реализации выбран **File System Access в MAIN-контексте Telegram**. Собственная кнопка открывает picker синхронно по доверенному пользовательскому клику. Подготовка метаданных происходит заранее; writer открывается только после получения места в общей очереди.

Метаданные и управление проходят через ISOLATED content script в MV3 service worker. Байты файла и файловый handle этот канал не пересекают. Источник, handle и writer остаются в исходной вкладке. Закрытие popup и навигация внутри Telegram SPA через `history.pushState`/`location.hash` сохраняют исполнителя. Настоящая перезагрузка или замена документа, уход с поддерживаемого Telegram Web и закрытие вкладки прерывают зависимую от страницы передачу.

В MAIN-контексте Zod вызывается с `jitless: true` для каждой проверки. Telegram Web A добавляет meta CSP после document_start: ранняя проверка доступности eval иначе разрешает JIT, который позднее уже запрещён. Настройки глобального Zod страницы не изменяются. Этот сценарий воспроизводится отдельным E2E.

Web K использует доступный runtime `requestFilePart` с точной inputFileLocation. Web A устанавливает узкий перехват Worker при document_start и использует существующий `downloadMedia` RPC. Оба варианта используют текущую авторизацию клиента, не копируют сессионные ключи и не запускают плеер. Подробнее — в документах адаптеров.

Документ читается порциями до 512 KiB. Запись каждой порции ожидается до чтения следующей. Проверяются известный полный размер, неизменность размера, границы и завершение. В Web A фото возвращается целиком существующим API; для этого отдельного пути установлен предел 32 MiB. Предел документов исполнителя — 4 GiB. Эти технические пределы не заменяют живые измерения.

После полной передачи начинается короткая финализация: новая отмена уже не принимается, writer закрывается. Только успешное `close()` даёт `completed`. Ошибка чтения/записи приводит к `abort()`; ранее принятая отмена и закрытие страницы проверяются до `close()`. Если файл уже успешно закрыт, результат — завершённая загрузка.

MV3 worker хранит только задания, настройки и связи с источником. IndexedDB-транзакция выдаёт одно место в очереди. После пробуждения координатор опрашивает живые исполнители, восстанавливает пропущенные события и не запускает вторую копию по одному факту тайм-аута. Подтверждённая замена документа или утрата исходной вкладки делает зависимые задания прерванными. Повтор создаёт новую попытку с новым ID и тем же ключом медиа; история старого результата сохраняется.

Chrome отправляет `tabs.onUpdated` со статусом `loading` также при hash/pushState-навигации. Координатор проверяет текущего исполнителя через `probe` и сохраняет его сессию. Отсутствие ответа при существующей Telegram-вкладке само по себе не отзывает writer: новая страница подтверждает замену сессии сообщением `hello`. Уход на неподдерживаемый URL и закрытие вкладки обрабатываются отдельно. Так смена чата внутри SPA не превращает живое задание в `interrupted` и не запускает дублирующую загрузку.

Пауза, докачка с прежнего байта, скрытая постоянная работа без вкладки и сохранение без системного диалога в этой реализации не заявлены. `chrome.downloads`/offscreen не включены, поскольку выбранному пути не нужны их разрешения.

Протоколы исследованы по официальным исходникам и публичным production-бандлам. Автоматические проверки используют собственные fixtures: E2E работает с настоящим OPFS writer, но подменяет нативный picker ([описание E2E](../../tests/e2e/README.md)). Такие проверки не заменяют скачивание из настоящего Telegram. Актуальные количества тестов, живые результаты по клиентам, браузерам и форматам, а также ещё не проверенные случаи ведутся только в [таблице совместимости](../compatibility.md).
