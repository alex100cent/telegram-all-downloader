# File transfer and lifecycle

The first implementation uses **File System Access in Telegram's MAIN context**. The extension's button opens the picker synchronously on a trusted user click. Metadata is prepared in advance; the writer is opened only after a slot is obtained in the shared queue.

Metadata and control pass through the ISOLATED content script to the MV3 service worker. File bytes and the file handle do not cross this channel. The source, handle, and writer remain in the original tab. Closing the popup and navigating within the Telegram SPA through `history.pushState`/`location.hash` preserve the executor. An actual reload or document replacement, leaving a supported Telegram Web page, and closing the tab interrupt the transfer that depends on the page.

In the MAIN context, Zod is called with `jitless: true` for every validation. Telegram Web A adds a meta CSP after document_start: otherwise, an early eval availability check enables JIT that is later prohibited. The page's global Zod settings are not changed. A dedicated E2E test reproduces this scenario.

Web K uses the available `requestFilePart` runtime method with an exact inputFileLocation. Web A installs a narrowly scoped Worker hook at document_start and uses the existing `downloadMedia` RPC. Both paths use the client's current authorization, do not copy session keys, and do not start the player. See the adapter documents for details.

Documents are read in chunks of up to 512 KiB. Each write is awaited before the next chunk is read. The known total size, size stability, boundaries, and completion are checked. In Web A, the existing API returns a photo in full; this separate path has a 32 MiB limit. The executor's document limit is 4 GiB. These technical limits do not replace live measurements.

After the full transfer, a short finalization phase begins: new cancellation requests are no longer accepted and the writer is closed. Only a successful `close()` produces `completed`. A read/write error results in `abort()`; previously accepted cancellation and page closure are checked before `close()`. If the file has already been closed successfully, the result is a completed download.

The MV3 worker stores only jobs, settings, and source associations. An IndexedDB transaction allocates one queue slot. On waking, the coordinator probes live executors, recovers missed events, and does not launch a second copy merely because of a timeout. Confirmed document replacement or loss of the original tab interrupts dependent jobs. A retry creates a new attempt with a new ID and the same media key; the previous result remains in history.

Chrome also sends `tabs.onUpdated` with status `loading` for hash/pushState navigation. The coordinator checks the current executor through `probe` and preserves its session. A missing response while the Telegram tab still exists does not by itself revoke the writer: a new page confirms session replacement with a `hello` message. Navigation to an unsupported URL and tab closure are handled separately. As a result, changing chats within the SPA does not turn a live job into `interrupted` or start a duplicate download.

## Batches and destination folder (0.2.0)

The Telegram panel shows up to 200 discovered attachments, including individual items in a visible album. Refreshing the list explicitly clears selections that have disappeared; it does not scan history or scroll automatically. The selection retains the exact identity and resolver of the original candidate. Before writing, the resolver is called again; a change to account/peer/message/media/variant, MIME, or known size stops that file. Waiting for the resolver is cancellable: a source that arrives late is released without opening a writer.

The user invokes `showDirectoryPicker({ mode: 'readwrite' })` synchronously through the panel button. The folder handle remains only in the original page's memory. It is neither sent to the extension nor stored in IndexedDB. Each file gets a regular job in the shared sequential queue; `batchId`, a readable batch label, and the actual destination filename are added to history. A shared folder does not create a separate executor. Picker and permission requirements are described in the [Chrome File System Access documentation](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access).

Permission checks and selection of a specific safe filename occur after obtaining a slot, before opening the writer. By default, a collision preserves both files by adding a suffix; `skip` mode creates a terminal `skipped` state without reading bytes or modifying the existing file; `overwrite` must be enabled explicitly. The API does not provide atomic exclusive creation: an external program creating a file with the same name between the check and handle acquisition remains a limitation. The extension itself does not launch concurrent writers. A write error or cancellation preserves the previous file until a successful `close()`; creating a new file may leave an empty placeholder.

The manager is a separate extension page, `manager.html`, using the same coordinator and history. Closing the manager does not stop the batch. Bulk cancellation temporarily pauses allocation of new slots and cancels waiting jobs first; an unknown state of a live writer does not release its reservation. An unresponsive source is probed for cancellation once per tab/session within the operation. Retrying selected failed jobs opens the panel with their identities and requires a new folder selection. After the original page is lost, an individual retry opens the message link; there is no automatic folder recovery or download resumption.

This implementation does not claim support for pausing, resuming from the previous byte, continuous background operation without a tab, or saving without an explicit destination selection. `chrome.downloads`/offscreen are not enabled because the chosen path does not need their permissions.

The protocols were researched using official sources and public production bundles. Automated checks use project fixtures: E2E uses a real OPFS writer but substitutes the native picker ([E2E description](../../tests/e2e/README.md)). These checks do not replace downloads from real Telegram. Current test counts, live results by client, browser, and format, and cases that remain untested are maintained only in the [compatibility matrix](../compatibility.md).
